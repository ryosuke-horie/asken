# TDDコマンド

このコマンドはtdd-guideエージェントを呼び出し、テスト駆動開発の方法論を強制します。

## テストフレームワーク

- Go: 標準`testing`パッケージ + testify
- iOS: Swift Testing + Mockolo

```bash
# テスト実行
task test       # Go
task ios:test   # iOS

# カバレッジ付きでテスト実行
task test:coverage       # Go
task ios:test:coverage   # iOS
```

## このコマンドの機能

1. インターフェースのスキャフォールド - 最初に型/インターフェースを定義
2. テストを先に生成 - 失敗するテストを書く（RED）
3. 最小限のコード実装 - 通すのに十分なコードだけを書く（GREEN）
4. リファクタリング - テストをグリーンに保ちながらコードを改善（REFACTOR）
5. カバレッジ確認 - 80%以上のテストカバレッジを確保

## 使用タイミング

`/tdd`を使用する場合:
- 新機能を実装する時
- 新しい関数/コンポーネントを追加する時
- バグ修正時（まずバグを再現するテストを書く）
- 既存コードのリファクタリング時
- 重要なビジネスロジックを構築する時

## TDDサイクル

```
RED → GREEN → REFACTOR → REPEAT

RED:      失敗するテストを書く
GREEN:    通すための最小限のコードを書く
REFACTOR: コードを改善、テストはグリーンを維持
REPEAT:   次の機能/シナリオへ
```

## テストの種類

ユニットテスト（関数レベル）:
- ハッピーパスシナリオ
- エッジケース（空、nil、最大値）
- エラー条件
- 境界値

統合テスト（コンポーネントレベル）:
- APIエンドポイント（httptest）
- Firestoreエミュレータでのデータベース操作
- 外部サービス呼び出し

E2Eテスト:
- XCUITestで重要なユーザーフロー

## カバレッジ要件

- 80%最小 - 全コード

外部サービス連携（Gemini API等）は100%カバレッジを目指すと非現実的なため、80%を基準とする。重要なのはカバレッジの数値よりも、ビジネスロジックの振る舞いが正しくテストされていること。

## 他のコマンドとの連携

- `/plan`を最初に使用して何を構築するか理解
- `/tdd`を使用してテスト付きで実装
- `/code-review`を使用して実装をレビュー
