# TDDコマンド

このコマンドはtdd-guideエージェントを呼び出し、テスト駆動開発の方法論を強制します。

## テストフレームワーク

このプロジェクトではJestを使用します。

```bash
# テスト実行
npm test

# カバレッジ付きでテスト実行
npm test -- --coverage

# watchモードでテスト実行
npm test -- --watch
```

## このコマンドの機能

1. インターフェースのスキャフォールド - 最初に型/インターフェースを定義
2. テストを先に生成 - 失敗するテストを書く（RED）
3. 最小限のコード実装 - 通すのに十分なコードだけを書く（GREEN）
4. リファクタリング - テストをグリーンに保ちながらコードを改善（REFACTOR）
5. カバレッジ確認 - 80%以上のテストカバレッジを確保

## 使用タイミング

`/tdd`を使用する場合:
- 新機能を実装する時
- 新しい関数/コンポーネントを追加する時
- バグ修正時（まずバグを再現するテストを書く）
- 既存コードのリファクタリング時
- 重要なビジネスロジックを構築する時

## TDDサイクル

```
RED → GREEN → REFACTOR → REPEAT

RED:      失敗するテストを書く
GREEN:    通すための最小限のコードを書く
REFACTOR: コードを改善、テストはグリーンを維持
REPEAT:   次の機能/シナリオへ
```

## テストの種類

ユニットテスト（関数レベル）:
- ハッピーパスシナリオ
- エッジケース（空、null、最大値）
- エラー条件
- 境界値

統合テスト（コンポーネントレベル）:
- APIエンドポイント
- データベース操作
- 外部サービス呼び出し
- フック付きReactコンポーネント

E2Eテスト:
- 重要なユーザーフロー
- 複数ステップのプロセス
- フルスタック統合

## カバレッジ要件

- 80%最小 - 全コード

外部サービス連携（Gemini API等）は100%カバレッジを目指すと非現実的なため、80%を基準とする。重要なのはカバレッジの数値よりも、ビジネスロジックの振る舞いが正しくテストされていること。

## ベストプラクティス

推奨:
- 実装の前にテストを書く
- 各変更後にテストを実行し失敗を確認
- テストを通す最小限のコードを書く
- テストがグリーンになってからのみリファクタリング
- エッジケースとエラーシナリオを追加
- 80%以上のカバレッジを目指す

非推奨:
- テストの前に実装を書く
- 各変更後のテスト実行をスキップ
- 一度に多くのコードを書く
- 失敗するテストを無視
- 実装詳細をテスト（振る舞いをテスト）
- 全てをモック（統合テストを優先）

## 重要な注意事項

必須: テストは実装より前に書く。TDDサイクルは:

1. RED - 失敗するテストを書く
2. GREEN - テストを通すための実装
3. REFACTOR - コードを改善

REDフェーズを飛ばさない。テストを書く前にコードを書かない。

## 他のコマンドとの連携

- `/plan`を最初に使用して何を構築するか理解
- `/tdd`を使用してテスト付きで実装
- `/build-fix`を使用してビルドエラーが発生した場合に修正
- `/code-review`を使用して実装をレビュー
